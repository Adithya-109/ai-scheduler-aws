# Benchmark evaluation: AI Scheduler vs cloud-only, edge-only and other baselines

Generated by `bench/paper_eval.py` on 2026-10-28 22:13 (python 3.13.1, scikit-learn 1.9.1, 2000 bootstrap resamples). All policies are scored on **measured** edge and cloud run times. The AI Scheduler and the static-threshold baseline only use predictions made with the script's whole family held out of training (grouped K-fold), so these are out-of-sample numbers.

## Headline

* **With a real hardware gap** (edge 0.5 CPU vs cloud 4 CPU, 110 ms RTT): the AI Scheduler finishes all 633 jobs in **264 s**, 23.9% faster than edge-only (95% CI [-31.6, -17.1]%) and 16.3% faster than cloud-only; it is 0.6% from the oracle (99.4% oracle efficiency).
* Without the heavy workloads (591 jobs): -6.9% vs edge-only (CI [-11.1, -3.7]%), -12.4% vs cloud-only.
* **Routing accuracy** (chose the node that was really faster): 96.2% / 93.2% / 99.4% on the three datasets; MCC 0.853 / 0.590 / -0.003. On jobs where the choice matters by ≥10% the accuracy is 97.9% / 95.4% / 99.6%.
* **Latency-prediction accuracy** (log10 R², families held out): edge 0.965, cloud 0.973 (asymmetric + heavy); median absolute error 4% edge, 3% cloud.
* **Similar hardware** (the original edge vs EC2 data): the cloud is faster on only 1/495 jobs once RTT is paid, so there is nothing to gain; the scheduler is +3.1% vs edge-only and -40.3% vs cloud-only.
* **A tuned one-feature heuristic is a strong baseline.** Offloading whenever the static cost estimate exceeds a threshold (tuned on training folds) is -10.8% vs edge-only on the 591-job set, *better* than the AI Scheduler there (-6.9%), because the scheduler under-offloads (recall 52%). On the 633-job set the scheduler wins (-23.9% vs -22.3%), with far fewer wrong offloads (precision 90% vs 56%).
* **Overhead**: one scheduling decision takes 5.6 ms (p50), 12.5 ms (p95).

## Unseen hand-written workloads

On 16 hand-written scripts that the dataset generator never produced (`holdout/`), the static cost estimate has Spearman ρ = 0.39 with measured run time (`bench/holdout.py`). This is the weakest link: the regressors are only as good as the static features on code unlike the training families.

## How to read these results (threats to validity)

* The asymmetric datasets come from two Docker workers on one laptop with different CPU quotas and a **simulated** 110 ms RTT. They test the decision logic on a real compute gap; they are not an EC2 measurement. Only the similar-hardware dataset used a real cloud instance.
* The 42 heavy workloads in `asym_v2` were written to exercise the cloud; asym_v1 is the less favourable, more representative mix. Report both.
* Accuracy alone is misleading on the similar-hardware data (one positive in 495): always answering *edge* already scores 99.8%. Use balanced accuracy, MCC and the time-based metrics there.
* Each job was timed 3× (median kept); run-to-run noise on sub-50 ms jobs is comparable to the edge/cloud gap, which is why the *decisive* subset is reported.
* Single collection run per dataset; the bootstrap intervals capture workload variation, not machine-to-machine variation.
